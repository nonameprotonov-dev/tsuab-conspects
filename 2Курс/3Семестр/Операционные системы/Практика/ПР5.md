«Создание процесса Windows»

**Цель:** исследовать жизненный цикл процессов и потоков в Windows и WSL2, сравнить модели управления процессами, понять роль изоляции, планирования и защиты.

**ОС:** Windows 10/11, WSL2 Ubuntu.  
**Инструменты:** PowerShell, Process Explorer, Visual Studio / VS Code + MinGW, WSL2, GCC.

---

## Теоретическая часть

**Windows API** — набор функций, структур и интерфейсов, предоставляемых Windows для разработки приложений. Основные библиотеки: `kernel32.dll` (процессы, память, файлы), `user32.dll` (окна, сообщения), `gdi32.dll` (графика), `advapi32.dll` (реестр, безопасность).

Создание процесса в Windows выполняется функцией `CreateProcessA` или `CreateProcessW`. Она принимает командную строку, структуры `STARTUPINFOA` и `PROCESS_INFORMATION`, возвращает дескрипторы процесса и потока. Для ожидания завершения используется `WaitForSingleObject`, для освобождения ресурсов — `CloseHandle`.

В Linux процесс создаётся через `fork()` — копирование текущего процесса, и `exec()` — замена образа программы. Ожидание выполняется через `wait()` или `waitpid()`.

## Создание и наблюдение процесса в Windows

**Команды PowerShell:**

```powershell
Start-Process notepad.exe
$notepadPid = (Get-Process notepad).Id
Write-Host "PID Блокнота: $notepadPid"
```
![[2Курс/3Семестр/Операционные системы/Практика/Attachments/Pasted image 20260917182115.png]]

В **Process Explorer** находим процесс `notepad.exe` и фиксируем:

- количество потоков — обычно 4–8;
- User Time / Kernel Time;
- Working Set — объём физической памяти.

**Почему у простого приложения несколько потоков?**  
Даже простой Блокнот использует несколько потоков: главный UI-поток, поток обработки сообщений, потоки ввода-вывода, служебные потоки Windows. Это нужно для отзывчивости интерфейса и фоновых операций.

**Что означает, если Kernel Time растёт при сохранении файла?**  
Сохранение файла — это системные вызовы к файловой системе, диску и менеджеру памяти. Эти операции выполняются в режиме ядра, поэтому увеличивается `PrivilegedProcessorTime` (Kernel Time).

## Создание и наблюдение процесса в WSL2

**Команды в Ubuntu (WSL2):**

```bash
sleep 300 &
MYPID=$!
ps -T -p $MYPID
cat /proc/$MYPID/status | grep -E "Threads|VmRSS"
```
![[2Курс/3Семестр/Операционные системы/Практика/Attachments/Pasted image 20260918122316.png]]

**Почему у `sleep` только 1 поток?**  
`sleep` — простейшая программа, которая просто ждёт истечения таймера. Ей не нужны дополнительные потоки. Она вызывает `nanosleep()` и засыпает.

**Что хранится в `/proc/<PID>/`? Это реальные файлы?**  
`/proc` — виртуальная файловая система. Файлы в ней не существуют на диске, а генерируются ядром при обращении. Там хранится информация о процессе: `status`, `cmdline`, `fd`, `maps` и т. д.

## Принудительное завершение процесса

**Windows:**

```powershell
Stop-Process -Name notepad -Force
```
![[2Курс/3Семестр/Операционные системы/Практика/Attachments/Pasted image 20260918122743.png]]

**WSL2:**

```bash
kill -9 <PID>
```
![[2Курс/3Семестр/Операционные системы/Практика/Attachments/Pasted image 20260918122714.png]]

**В чём разница между мягким и принудительным завершением?**  
Мягкое завершение посылает запрос на закрытие (`SIGTERM` / `WM_CLOSE`). Процесс может сохранить данные, закрыть файлы, освободить ресурсы. Принудительное (`SIGKILL` / `TerminateProcess`) немедленно уничтожает процесс без возможности что-либо сделать.

**Может ли процесс игнорировать `kill -9`? А `Stop-Process -Force`?**  
`kill -9` (SIGKILL) не может быть перехвачен или проигнорирован. Ядро уничтожает процесс. `Stop-Process -Force` вызывает `TerminateProcess`, который также не может быть проигнорирован. Исключение — защищённые процессы (PPL), недоступные даже администратору.

## Попытка завершить защищённый процесс

**Windows:**

```powershell
Stop-Process -Name winlogon
```
![[2Курс/3Семестр/Операционные системы/Практика/Attachments/Pasted image 20260918122811.png]]

**WSL2:**

```bash
sudo kill -9 1
```
![[2Курс/3Семестр/Операционные системы/Практика/Attachments/Pasted image 20260918122928.png]]

**Какая ситуация возникает? Почему?**  
Windows: доступ запрещён, так как `winlogon` — критический системный процесс, защищённый механизмом PPL.  
WSL2: `Operation not permitted`, так как PID 1 — это `init`, который управляет всей сессией WSL2. Его убийство приведёт к остановке WSL2.

**Что такое Protected Process Light (PPL) в Windows?**  
PPL — механизм защиты процессов, при котором даже администратор не может завершить или изменить защищённый процесс. Доступ разрешён только подписанным компонентам Microsoft с соответствующими правами.

**Почему `init` (PID=1) нельзя убить даже через `sudo`?**  
Ядро Linux наделяет PID 1 особыми правами и защитой. Он обрабатывает сигналы иначе, а его завершение означает крах системы или в WSL2 — остановку виртуальной машины. Ядро не позволяет послать ему `SIGKILL`.

Наблюдение в Process Explorer и `top` / `htop`.

**Сколько потоков создаёт `yes`? А PowerShell-цикл?**  
`yes` — однопоточная программа, создаёт 1 поток.  
PowerShell-цикл в `Start-Job` выполняется в отдельном процессе задания; сам цикл занимает один рабочий поток, но PowerShell может иметь несколько служебных потоков.

**Как ОС делит CPU между процессами?**  
Планировщик выделяет каждому потоку квант времени. По истечении кванта или при блокировке происходит переключение контекста. Приоритеты и политики планирования определяют, кто получит CPU следующим.

**Почему `yes` использует 100% одного ядра, а не всех?**  
`yes` — однопоточный процесс. Один поток может выполняться только на одном логическом процессоре в данный момент. Чтобы загрузить все ядра, нужно запустить несколько экземпляров или многопоточную программу.

## Сравнительный анализ

| Аспект | Windows | Linux (WSL2) | Вывод |
|---|---|---|---|
| Создание процесса | `CreateProcess()` / `Start-Process` | `fork()` + `exec()` | Linux разделяет на два этапа |
| Представление процесса | Объект ядра + `EPROCESS` | `task_struct` + `/proc` | Linux использует виртуальную ФС |
| Защита системных процессов | PPL, VBS | `CAP_SYS_ADMIN`, PID=1 | Обе ОС защищают ядро |
| Модель потоков | Thread = объект ядра | Thread = легковесный процесс (`clone`) | Windows более «тяжёлая» модель |

## Код лаунчера Windows (`createprocess.cpp`)

```cpp
#include <windows.h>
#include <stdio.h>

int main(int argc, char* argv[])
{
    STARTUPINFOA si;
    PROCESS_INFORMATION pi;

    ZeroMemory(&si, sizeof(si));
    si.cb = sizeof(si);
    ZeroMemory(&pi, sizeof(pi));

    if (argc != 2)
    {
        printf("Usage: %s [cmdline]\n", argv[0]);
        return 1;
    }

    char* cmdline = _strdup(argv[1]);

    if (!CreateProcessA(
        NULL,
        cmdline,
        NULL,
        NULL,
        FALSE,
        0,
        NULL,
        NULL,
        (LPSTARTUPINFOA)&si,
        &pi))
    {
        printf("CreateProcess failed (%d).\n", GetLastError());
        free(cmdline);
        return 1;
    }

    WaitForSingleObject(pi.hProcess, INFINITE);

    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);
    free(cmdline);
    return 0;
}
```

**Компиляция:**

```cmd

```

**Запуск:**


## Код лаунчера Linux (`linux_launcher.c`)

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

int main(int argc, char *argv[])
{
    if (argc < 2) {
        printf("Usage: %s command [args...]\n", argv[0]);
        return 1;
    }

    pid_t pid = fork();

    if (pid == 0) {
        execvp(argv[1], &argv[1]);
        perror("execvp");
        return 1;
    } else if (pid > 0) {
        wait(NULL);
    } else {
        perror("fork");
        return 1;
    }

    return 0;
}
```

**Компиляция в WSL2:**

```bash
gcc linux_launcher.c -o linux_launcher
```

**Запуск:**

```bash
./linux_launcher ls
./linux_launcher sleep 10
```

## Сравнение с PowerShell

| Действие | Лаунчер | `Start-Process` |
|---|---|---|
| Создание процесса | `CreateProcess` | .NET → `CreateProcess` |
| Ожидание завершения | `WaitForSingleObject` | Флаг `-Wait` |
| Освобождение ресурсов | `CloseHandle` | Автоматически (финализатор) |

**Какой подход «ближе» к ядру ОС?**  
Лаунчер на Win32 API ближе к ядру, так как напрямую вызывает `CreateProcessA` из `kernel32.dll`. PowerShell работает через .NET, который скрывает детали.

**Почему в .NET не нужно вызывать `CloseHandle` явно?**  
.NET использует `SafeHandle` и финализаторы. Сборщик мусора и специальные обёртки автоматически освобождают дескрипторы, когда объект больше не используется.

**Что произойдёт, если убрать `CloseHandle` из вашего кода?**  
Возникнет утечка дескрипторов. Каждый запуск лаунчера будет оставлять открытые handles на процесс и поток. Со временем их количество исчерпает лимит, и новые операции с процессами и файлами станут невозможны.

## Эксперименты с лаунчером

### Передача аргументов

```cmd
createprocess.exe "notepad.exe C:\test.txt"
```

Работает, если `notepad.exe` доступен в `PATH`. `CreateProcessA` принимает всю строку как командную строку. Если путь содержит пробелы, его нужно заключать в кавычки.

### Убираем ожидание

Закомментировать:

```cpp
// WaitForSingleObject(pi.hProcess, INFINITE);
```

Лаунчер завершится сразу после создания дочернего процесса. Дочерний процесс продолжит работу как фоновый. Это демонстрирует, что родитель не обязан ждать потомка.

### Утечка дескрипторов

Закомментировать:

```cpp
// CloseHandle(pi.hProcess);
// CloseHandle(pi.hThread);
```

Запустить лаунчер 10 раз. В Process Explorer включить столбец `Handles`. Количество дескрипторов будет расти, хотя процессы завершились. Это утечка handles. Она показывает важность явного управления ресурсами в системном программировании.

## Сравнение с Linux

**Чем отличается `fork/exec` от `CreateProcess`?**  
В Linux создание процесса разделено: `fork()` создаёт копию текущего процесса, `exec()` заменяет образ на новую программу. В Windows `CreateProcess` выполняет обе операции за один вызов: создаёт процесс и загружает в него указанную программу.

**Почему в Linux нет `CloseHandle`?**  
В Linux дескрипторы — это целые числа. Они автоматически закрываются при завершении процесса. Для явного закрытия используется `close()`. Нет объектов ядра, которые требуют обязательного `CloseHandle`, как в Windows.

**Какая модель проще? Безопаснее?**  
`fork/exec` концептуально проще для UNIX, но может быть неэффективен и сложен для многопоточных программ. `CreateProcess` более монолитный и явный. Безопасность: Windows даёт больше контроля через дескрипторы и права доступа, Linux использует права файлов и capabilities. Обе модели безопасны при правильном использовании.

## Гонки и изоляция

**Почему появились дубликаты?**  
Три экземпляра скрипта одновременно читают и записывают `/tmp/counter.txt`. Между чтением и записью планировщик может переключить процесс, поэтому два скрипта читают одно и то же значение и записывают одинаковый результат. Возникает состояние гонки.

**Как это связано с изоляцией процессов?**  
Изоляция защищает память и CPU, но не внешние общие ресурсы — файлы. Процессы изолированы, но файл общий. Это показывает, что нужны механизмы синхронизации.

**Как исправить?**  
Использовать блокировки: `flock`, `mutex`, семафоры. Например, в bash можно использовать `flock` или создавать lock-файл. В C — `pthread_mutex` или файловые блокировки.

## Ответы на контрольные вопросы

**Какие механизмы используются для создания процессов в Windows и Linux? В чём принципиальная разница?**  
Windows: `CreateProcess` или `CreateProcessAsUser`, `ShellExecute`. Linux: `fork()` + `exec()`, `clone()`, `posix_spawn()`. Принципиальная разница: Windows создаёт процесс и загружает программу одним вызовом, возвращая дескрипторы. Linux сначала копирует процесс, затем заменяет образ.

**Почему нельзя завершить системные процессы? Как это связано с надёжностью ОС?**  
Системные процессы (`winlogon`, `csrss`, `init`) критичны для работы ОС. Их завершение приводит к краху или нестабильности. Windows защищает их через PPL, Linux — через особый статус PID 1 и capabilities. Это обеспечивает надёжность и устойчивость системы.

**Приведите пример, когда изоляция процессов не спасает от конфликтов.**  
Гонка за ресурс: несколько процессов одновременно пишут в один файл `/tmp/counter.txt`. Изоляция памяти и CPU не защищает общий файл. Возникают дубликаты и потерянные обновления. Нужны блокировки — мьютексы, файловые блокировки.

**Как ОС обеспечивает справедливое распределение CPU? Что происходит при 100% нагрузке?**  
Планировщик выделяет кванты времени, учитывает приоритеты и политики. При 100% нагрузке один поток занимает одно ядро. Если потоков больше, чем ядер, они делят время. Система остаётся отзывчивой благодаря приоритетам и вытесняющей многозадачности.

**Как работает ваш лаунчер на уровне Win32 API?**  
Лаунчер вызывает `CreateProcessA`, передавая командную строку, `STARTUPINFOA` и `PROCESS_INFORMATION`. Затем `WaitForSingleObject` ожидает завершения дочернего процесса. `CloseHandle` закрывает дескрипторы. Это низкоуровневое управление жизненным циклом процесса.

**Что происходит при утечке хэндлов? Как это обнаружить?**  
Незакрытые дескрипторы накапливаются в таблице ядра. Со временем исчерпывается лимит, новые операции с файлами и процессами невозможны. Обнаружить можно в Process Explorer по столбцу Handles, через `Get-Process | Select HandleCount`, мониторингом системы.

**Сравните модели создания процессов в Windows и Linux на примере ваших лаунчеров.**  
Windows-лаунчер: один вызов `CreateProcess`, возвращает дескрипторы, требует `CloseHandle`. Linux-лаунчер: `fork()` создаёт копию, `execvp()` заменяет образ, `wait()` ожидает завершения. Windows более явная работа с дескрипторами, Linux использует файловые дескрипторы и автоматическое освобождение при завершении.
